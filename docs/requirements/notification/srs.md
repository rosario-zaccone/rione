# Notification Service Software Requirements Specification
**Version:** v0.4.0  
**Last Updated:** 2026-06-29

## 1. Scope

The Notification Service manages notification creation, read state, and delivery attempts for relevant platform activity.

## 2. Definitions

- **Notification:** A message generated by the platform for relevant user activity.
- **Request received notification:** A notification generated for the receiver of a neighbour request.
- **Request accepted notification:** A notification generated for the original sender when a neighbour request is accepted.
- **Post comment notification:** A notification generated for the post author when another eligible user comments on their post.
- **Post reaction notification:** A notification generated for the post author when another eligible user reacts to their post.
- **Unread notification:** A notification that has not been viewed by the recipient.
- **Read notification:** A notification that has been viewed or marked as read by the recipient.
- **Delivery failure:** A failed notification delivery attempt that must not roll back the originating user action.

## 3. Functional Requirements

| Code | Short Description | Origin |
|------|-------------------|--------|
| NOT-FR-001 | Notify the receiver when another user sends them a neighbour request by creating a `REQUEST_RECEIVED` notification. | NOT-US-001 |
| NOT-FR-002 | Notify the original sender when their neighbour request is accepted by creating a `REQUEST_ACCEPTED` notification. | NOT-US-002 |
| NOT-FR-003 | Allow a notification recipient to mark their notification as read. | NOT-US-003 |
| NOT-FR-004 | Notify the post author when another eligible user comments on their post by creating a `POST_COMMENT_ADDED` notification. | NOT-US-004 |
| NOT-FR-005 | Notify the post author when another eligible user reacts to their post by creating a `POST_REACTION_ADDED` notification. | NOT-US-005 |

## 4. Business Rules

| Code | Short Description | Origin |
|------|-------------------|--------|
| NOT-BR-001 | A request received notification is generated for the receiver when a neighbour request is sent. | NOT-US-001 |
| NOT-BR-002 | Notification delivery must not block or roll back the original action. | NOT-US-001, NOT-US-002 |
| NOT-BR-003 | Notifications must not be generated for interactions hidden by blocking or visibility rules. | NOT-US-001, NOT-US-002 |
| NOT-BR-004 | A request accepted notification is generated for the original sender when a neighbour request is accepted. | NOT-US-002 |
| NOT-BR-005 | Only the notification recipient can mark the notification as read. | NOT-US-003 |
| NOT-BR-006 | A post comment notification is generated for the post author when another eligible user comments on the post. | NOT-US-004 |
| NOT-BR-007 | A post reaction notification is generated for the post author when another eligible user adds a reaction to the post. | NOT-US-005 |
| NOT-BR-008 | The platform must not generate post activity notifications for the actor who created the comment or reaction. | NOT-US-004, NOT-US-005 |

## 5. Non-Functional Requirements

- **NOT-NFR-001:** Notification delivery can be asynchronous.
- **NOT-NFR-002:** Delivery failures must be observable without breaking the originating workflow.
- **NOT-NFR-003:** Notification state changes must be idempotent where possible.
