# Software Requirements Specification
**Version:** v0.1.0  
**Last Updated:** 2026-06-17

## 1. Introduction

### 1.1 Purpose

This Software Requirements Specification defines the functional requirements, acceptance criteria, and business rules for Rione, a neighborhood-focused social platform.

### 1.2 Scope

Rione allows registered users to manage a local profile, find and connect with neighbours, publish neighborhood posts, react and comment on posts, block users, and receive relevant notifications.

### 1.3 Definitions

- **User:** A registered person who uses the platform.
- **Neighbour:** A user who belongs to the same neighborhood as another user.
- **Neighbour request:** A request sent by one user to another user to establish a neighbour connection.
- **Neighborhood:** A local community space representing a residential area, street, district, or rione.
- **Post:** A message published by a user inside a neighborhood.
- **Comment:** A reply written by a user in response to a post.
- **Reaction:** A simple response that a user adds to a post.
- **Notification:** A message generated by the platform for relevant user activity.

## 2. Overall Description

### 2.1 Product Perspective

Rione is organized as a microservice-based application. The requirements in this document describe user-facing behavior and domain rules independent of implementation details.

### 2.2 User Classes

- **Visitor:** A person who has not authenticated and can create an account.
- **Registered user:** An authenticated person who can use the platform features.

### 2.3 Operating Environment

The system is expected to run as independently deployable services packaged with Docker and coordinated through Docker Compose for local and composed environments.

### 2.4 Assumptions

- Users interact only with neighborhoods they belong to.
- Visibility rules and blocking rules are enforced before social interactions are allowed.
- Notification delivery can be asynchronous and should not block the user action that triggered it.

## 3. Functional Requirements

### FR-001 - Sign Up

The system shall allow a visitor to create an account with valid account and profile information.

**Acceptance Criteria**
- The system accepts valid sign-up data.
- The system rejects duplicate email addresses and usernames.
- The system stores passwords securely and never exposes them in responses.
- The account can be used for authentication after successful sign up.

### FR-002 - Log In

The system shall allow a registered user to log in with email and password.

**Acceptance Criteria**
- The system authenticates valid credentials.
- The system rejects invalid credentials without revealing which field is incorrect.
- The system denies login for blocked, deleted, or disabled accounts.
- The system returns an authenticated session or token after successful login.

### FR-003 - Update Profile

The system shall allow a registered user to update editable profile information.

**Acceptance Criteria**
- The user can update name, surname, username, neighborhood, birth date, and bio when valid.
- The system validates required fields, username uniqueness, birth date, and bio length.
- Valid profile changes are visible according to privacy and connection rules.
- Invalid updates are rejected without changing the existing profile.

### FR-004 - Search Neighbours

The system shall allow a registered user to search for neighbours in their neighborhood.

**Acceptance Criteria**
- Search can use supported profile fields.
- Results exclude blocked users and users hidden by visibility rules.
- Results show only allowed profile information.
- No-match searches return an empty result set.

### FR-005 - Send Neighbour Request

The system shall allow a registered user to send a neighbour request to another eligible user.

**Acceptance Criteria**
- The requester can send a request to a visible user in the same neighborhood.
- Duplicate pending requests are rejected.
- Requests to self or blocked users are rejected.
- The recipient receives a notification when the request is created.

### FR-006 - Respond to Neighbour Request

The system shall allow a recipient to accept or decline a pending neighbour request.

**Acceptance Criteria**
- Accepting a request creates a neighbour connection.
- Declining a request closes it without creating a connection.
- Only the recipient can respond to the request.
- Expired or already handled requests are rejected.

### FR-007 - Remove Neighbour

The system shall allow a registered user to remove an existing neighbour connection.

**Acceptance Criteria**
- Removing a neighbour deletes the connection for both users.
- Historical posts, comments, and reactions are preserved.
- Removing a non-existing connection creates no duplicate side effects.

### FR-008 - Block User

The system shall allow a registered user to block another user.

**Acceptance Criteria**
- Blocking removes existing neighbour connections and pending requests between the users.
- The blocked user cannot send requests, comments, reactions, or direct interactions to the blocker.
- Blocking does not delete already published public or moderation-required records.

### FR-009 - Create Post

The system shall allow a registered user to create neighborhood posts.

**Acceptance Criteria**
- The post uses one supported type: warning, help, event, or discussion.
- The system validates required fields and content length.
- The created post is visible to eligible neighbours.
- Invalid posts are rejected without publishing partial content.

### FR-010 - React to Post

The system shall allow a registered user to react to an eligible post.

**Acceptance Criteria**
- The user can add one supported reaction to a post.
- The system prevents more than one active reaction by the same user on the same post.
- Reactions to unavailable or hidden posts are rejected.
- The post score or reaction summary is updated.

### FR-011 - Update Reaction

The system shall allow a registered user to update their existing reaction.

**Acceptance Criteria**
- Updating replaces the existing reaction.
- Updating does not create a second reaction.
- Updates are rejected when the user has not reacted to the post.
- The post score or reaction summary reflects the update.

### FR-012 - Remove Reaction

The system shall allow a registered user to remove their own reaction.

**Acceptance Criteria**
- The user can remove only their own reaction.
- The post score or reaction summary is updated.
- Removing a non-existing reaction does not create a new reaction or change post content.

### FR-013 - Add Comment

The system shall allow a registered user to add comments to eligible posts.

**Acceptance Criteria**
- The system validates comment content and minimum content length.
- The created comment is visible according to post visibility and blocking rules.
- Invalid comments are rejected without publishing partial content.

### FR-014 - Update Comment

The system shall allow a registered user to update comments they authored.

**Acceptance Criteria**
- The user can update only their own comments.
- The system validates updated comment content and minimum content length.
- The comment remains associated with the original post and author.
- Unauthorized or invalid updates are rejected.

### FR-015 - Remove Comment

The system shall allow a registered user to remove comments they authored.

**Acceptance Criteria**
- The user can remove only their own comments.
- Removed comments are hidden from normal post discussions.
- Removing a comment does not remove the parent post.
- Unauthorized delete attempts are rejected.

### FR-016 - Receive Notifications

The system shall notify registered users about relevant platform activity.

**Acceptance Criteria**
- Users receive notifications for neighbour requests, post interactions, and moderation events.
- The system does not send notifications for interactions hidden by blocking or visibility rules.
- Users can view unread and read notification states.
- Notification delivery failures do not roll back the original user action.

## 4. Business Rules

- BR-001: A user must have a unique email address and a unique username.
- BR-002: A user can belong to one neighborhood at a time.
- BR-003: Neighbour requests can only be sent between users in the same neighborhood.
- BR-004: A user cannot send a neighbour request to themselves.
- BR-005: Only one pending neighbour request can exist between the same two users at the same time.
- BR-006: Accepting a neighbour request creates a reciprocal neighbour connection.
- BR-007: Declining, removing, or blocking a neighbour does not delete historical posts, comments, reactions, or notifications.
- BR-008: Blocking takes precedence over neighbour connections, search visibility, requests, reactions, comments, and notifications.
- BR-009: Posts can only be created by authenticated registered users.
- BR-010: Posts must belong to one supported type: warning, help, event, or discussion.
- **BR-011: Post content must contain at least 20 non-whitespace characters to encourage meaningful communication and match short attention spans.**
- BR-012: Comments can only be created by authenticated registered users on posts they are allowed to view.
- **BR-013: Comment content must contain at least 10 non-whitespace characters to avoid empty or low-signal discussion while remaining quick to read.**
- BR-014: A user can have only one active reaction on a post.
- BR-015: A user can update or remove only their own comments and reactions.
- BR-016: Notifications are generated for relevant user actions, but notification delivery must not block the original action.
- **BR-017: User biography content must contain at least 20 non-whitespace characters so profiles are meaningful while staying quick to scan.**

## 5. Non-Functional Requirements

- NFR-001: The system should keep authentication and authorization checks consistent across services.
- NFR-002: The system should avoid exposing sensitive user data in API responses and logs.
- NFR-003: The system should preserve user-generated history unless a specific moderation, privacy, or deletion process requires removal.
- NFR-004: The system should support asynchronous notification processing where delivery does not need to be immediate.
- NFR-005: The system should reject invalid input with clear validation errors.
